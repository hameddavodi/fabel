- 2026-09-06 Golden files: `tools/make_golden.py` drives R through rpy2 when importable, else falls back to `Rscript` subprocess with the same seeded R scripts. Output format identical.
- 2026-09-06 Commit style: project CLAUDE.md conventional commits (`feat(basis): ...`) win over AISMA prefix scheme (project file overrides global, AISMA rule 1: adopt repo conventions).
- 2026-09-06 `getbasispenalty()` throws "Basis type not recognizable" for monomial and constant basis types in fda 6.3.0 (all nbasis tested); `eval.penalty()` works uniformly across all 7 basis types. `tools/golden_r/basis.R` uses `eval.penalty()` exclusively for consistency.
- 2026-09-06 B-spline penalty validity constraint empirically determined to be `Lfdobj <= norder - 2` (not the naive `Lfdobj < norder`); `getbasispenalty`/`eval.penalty` errors otherwise (e.g. order 3, Lfdobj 2 fails). Verified by systematic probing over norder 1-6 x Lfdobj 0-5.
- 2026-09-06 fda 6.3.0 exposes `sd.fd`, `stddev.fd`, `std.fd` as equivalent entry points (confirmed via `exists()`); `tools/golden_r/core.R` standardizes on `sd.fd`.
- 2026-09-06 `core.json` rtol set to 1e-6 (vs 1e-8 for `basis.json`): `inprod()` uses Richardson extrapolation, "good to about four to five significant digits" per fda's own docs.
- 2026-09-06 fda 6.3.0's `bifd()` is unconditionally broken for a 3-D coef array (`ndim == 3`, reps dim with no vars dim): its body sets `defaultnames` only in `if (ndim == 2)`/`if (ndim == 4)` branches (copy-paste bug omits `ndim == 3`) but then unconditionally runs `names(defaultnames) <- c(...)`, throwing "object 'defaultnames' not found" even when `fdnames` is passed explicitly (that line never references the `fdnames` arg). Worked around in `tools/golden_r/core.R` by using a 4-D array (`dim = c(nbasis_s, nbasis_t, nrep, nvar=1)`) instead, which hits the working `ndim == 4` branch and still exercises the reps dimension.
- 2026-09-06 GitHub Actions in `.github/workflows/ci.yml` pinned to full commit SHAs verified via `gh api repos/<owner>/<repo>/tags` (actions/checkout v7.0.1, astral-sh/setup-uv v10.0.1, actions/upload-artifact v7.0.1), each with a `# vX.Y.Z` comment.
- 2026-09-06 `parity` CI job runs on plain Python (uv-managed), no R/Docker: golden JSON files are pre-generated and committed, so parity tests only need `fabel` + the JSON, not R/rpy2. R is only needed to regenerate golden files via `make golden` / `tools/make_golden.py`.
- 2026-09-06 **JSON precision bug found by parity agent, fixed same day**: `jsonlite::toJSON(..., digits = NA)` looks like "full round-trip precision" but is actually only ~15 significant digits, which can silently move a value across a float boundary (e.g. a B-spline breakpoint at `0.30000000000000004` serialized as bare `0.3`, a *different* double). `tools/golden_r/common.R::finalize()` now uses `digits = 17` (jsonlite's documented round-trip setting); `basis.json`/`core.json` regenerated (case counts unchanged, only literal precision changed).
- 2026-09-06 Golden schema extended with an optional per-case `"rtol"` field (overrides `meta.rtol` for one case) for iterative fits (`smooth.monotone`, `smooth.pos`) that need a looser tolerance (1e-5) than the module default (1e-8). `tools/golden_r/common.R::add_case()`, `tests/parity/conftest.py::case_rtol()`, `tests/unit/test_golden_schema.py`, and `docs/dev/conventions.md` all updated to support it.
- 2026-09-06 `lambda2gcv(log10lambda, ...)` takes **log10-scale** lambda; `lambda2df(..., lambda)`/`df2lambda(..., df)` take **linear-scale** lambda/df. Asymmetric across three closely related fda functions — `tools/golden_r/smoothing.R` passes `seq(-4,8,by=0.25)` directly (not exponentiated) to `lambda2gcv` for the GCV grid.
- 2026-09-06 `Data2fd()`'s 4th positional argument is `nderiv`, not `lambda` (despite the task's `Data2fd(argvals, y, basis, lambda)` shorthand) — `lambda` must be passed by name in `tools/golden_r/smoothing.R`.
- 2026-09-06 Task spec for `smooth.monotone` on growth `hgtf` asked for "B-spline order 6, 13 basis (knots at ages)", but `create.bspline.basis(breaks=growth$age, norder=6)` with all 31 raw ages gives `nbasis=35` (`nbreaks + norder - 2`), not 13. Resolved with an independent design choice: a reduced 9-point break sequence (`seq(min(age), max(age), length.out=9)`) correctly yields `nbasis=13`. Not derived from any source.
- 2026-09-06 `fdepth()` requires its `data` argument shaped as `list(y = <matrix>)` (or `list(argvals=, y=)`) — passing a bare numeric matrix fails inside `fdepth()` with `"$ operator is invalid for atomic vectors"`.
- 2026-09-06 `Fperm.fd(yfdPar, xfdlist, betalist, ...)` produces `Fobs`/`Fvals`/`Fnull` identically `0` at every permutation when **every** `betalist` entry uses a constant basis (time-constant scalar coefficients) for a functional response with strong day-of-year structure — a degenerate result masquerading as "no effect" (the underlying model residual is actually large, `resid_norm ~1446` over 365x35 points). Using a genuine functional basis for `betalist` (same Fourier(25) basis as the response, matching every `fRegress` example in the public docs) gives a well-behaved, non-degenerate `Fobs` (0.4426). `tools/golden_r/stats.R`'s `fperm_case()` uses the latter design (intercept + Atlantic-region dummy, both with functional Fourier betas).
- 2026-09-06 fda 6.3.0's dataset catalog (`data(package="fda")$results[, "Item"]`) has no `CSTR` dataset and no separate "Chinese script" dataset — the task spec's request for both was based on a mistaken assumption. Full catalog (29 items) recorded in `tests/golden/datasets.json`'s `dataset_catalog` case. The handwriting-related dataset that does exist, `handwrit` (+ `handwritTime`), is covered instead.
- 2026-09-06 **inprod() precision bug found by parity agent, partially fixed**: `inprod()`'s public signature (`fdobj1, fdobj2, Lfdobj1, Lfdobj2, rng, wtfd`) exposes no `EPS`/`JMAX` knobs -- its help text states its Richardson/Romberg approximation is "good to about four to five significant digits", which is exactly the ~1.3e-4 relative mismatch the parity agent measured against the exact `t(coefs) %*% eval.penalty(...) %*% coefs`. For the 4 B-spline x B-spline cases (`inprod_bspline_L0_0/L1_1/L2_0/L0_2`), fda's public API has an exact alternative for plain-derivative orders on a B-spline basis: `inprod.bspline(fdobj1, fdobj2, nderiv1, nderiv2)`, confirmed to match the exact quadratic form to ~1e-14 (vs ~2e-5 to ~2.6e-1 for `inprod()`). `tools/golden_r/core.R` now uses `inprod.bspline()` for those 4 cases; `core.json` regenerated (still 28 cases). No equivalent exact function exists in fda's public API for Fourier-basis or mixed-basis inner products (`inprod_fourier_L0_0/L1_1/L2_2`, `inprod_basis_bspline_x_fourier`) -- those remain at R's own ~1e-4 accuracy; cannot be tightened without either exposing private EPS/JMAX internals (not public API) or hand-deriving analytic Fourier integrals ourselves (would stop being "R's actual output").
- 2026-09-06 (Eng 1) `LDO` lives in `src/fabel/_operator.py` and is re-exported from `core.py` and `__init__.py`. `basis.py` needs `LDO` for penalties and `core.py` needs `Basis`, so a shared leaf module is the only way to break the cycle without a runtime import.
- 2026-09-06 (Eng 1) B-spline right-endpoint convention: the last knot interval is closed when `deriv == 0 or order - deriv > 1`. Evaluating at the right endpoint must reproduce the limit from the left; for the top derivative of a spline that limit does not exist, so the half-open convention is kept there.
- 2026-09-06 (Eng 1) Product bases carry knot multiplicities: the product of splines of orders `k1, k2` with interior smoothness `s1, s2` is order `k1 + k2 - 1` with multiplicity `order - 1 - min(s1, s2)`. Merging plain breaks gives a space that is too smooth and cannot hold the product (measured 6e-2 absolute error before the fix, 1e-15 after). This is where Fabel deliberately diverges from `times.fd`, which is 12.8% off the exact product.
- 2026-09-06 (Eng 1) `.derivative(n)` is exact everywhere: each basis reports `(derivative_basis, coefficient_matrix)` from `_derivative_map`. The derivative of an order-k spline is the order-(k-n) spline on the same breaks, so no projection and no accuracy loss. `deriv.fd` instead re-expands in the original basis and is 1.3% off.
- 2026-09-06 (Eng 1) `FData ** p`: non-negative integers are exact repeated products in the product basis; every other exponent is projected onto a spline refined eightfold at order 6, because no basis holds a fractional power exactly. `FData / FData` raises `TypeError` -- the quotient is not closed in any supported basis. `fd +/- scalar` uses the L2 projection of the constant.
- 2026-09-06 (Eng 1) `.std()` projects the pointwise ddof=1 standard deviation sampled on `max(201, 10 * n_basis)` points. Exact whenever the deviation lies in the span; the pointwise sd of an arbitrary sample generally does not, so this is a projection by nature, not an approximation choice.
- 2026-09-06 (Eng 1) `_backend.result_namespace` treats NumPy as promotable: with a torch argument and NumPy coefficients the result is torch. `array_api_compat.array_namespace` raises on that mix, but it is exactly what a torch user hits when evaluating a NumPy-fitted curve.
- 2026-09-06 (Eng 1) `_backend.asarray` returns its argument unchanged when namespace and dtype already match. This preserves autograd graphs (the documented contract) and avoids torch's `requires_grad` deprecation warning.
- 2026-09-06 (Eng 1) `inprod`'s operator parameters are named `lfd1`/`lfd2`, lowercase, to satisfy ruff N803 without a per-file ignore.
- 2026-09-06 (Eng 1) Parity comparisons use `atol = 1e-12 * max(1.0, max|expected|)`. This scales the absolute floor with the magnitude of the case rather than loosening `rtol`, which stays at the golden file's `meta.rtol`.
- 2026-09-06 (Eng 1) Core parity compares function values on a shared 401-point grid rather than coefficients, so a result landing in a different but equivalent basis still matches. Coefficient comparison would falsely fail every case where Fabel's exact derivative or product basis differs from R's.
- 2026-09-06 (Eng 1) 17 basis cases and 7 core cases are strict xfails because R fda 6.3.0 is the less accurate side. Each carries the measured deviation and the mathematics in the `R_FDA_DEFECTS` dicts of `tests/parity/test_basis.py` and `test_core.py`. Strict, so a future golden regeneration that fixes one fails the suite instead of passing silently -- this is how the four `inprod_bspline_*` cases were caught and un-xfailed the same day.
- 2026-09-06 (Eng 1) Penalty and Gram matrices are memoised globally on the basis value (`_linalg.cached_gram`), not per instance. `benchmarks/test_bench_basis.py` therefore clears the cache each round; a freshly constructed but equal basis is a cache hit, and timing it measured a dict lookup (8 us) instead of the quadrature (285 us).
- 2026-09-06 (Eng 1) Plot tests assert the vertex data handed to the renderer rather than an image hash. An image hash pins fonts, DPI, the matplotlib version and the platform, none of which the plotting code controls; comparing `Line2D.get_xydata()` against the curve values pins exactly what the mixin is responsible for and is stable across all of them.
## Failed approaches (do not retry)
- Naive B-spline penalty Lfdobj bound `Lfdobj < norder` (from initial task heuristic): fails for e.g. order 3, Lfdobj 2. Correct bound is `Lfdobj <= norder - 2`.
- Passing `fdnames` explicitly to `bifd()` to work around its 3-D `defaultnames` bug: does not help, since the crashing line (`names(defaultnames) <- ...`) never reads the `fdnames` argument. Must avoid ndim==3 arrays entirely (use ndim==2 or ndim==4).
- `jsonlite::toJSON(..., digits = NA)` as "full precision" for golden files: it is not (see Decisions above). Always use `digits = 17`.
- Representing scalar/dummy covariates in `fRegress`/`Fperm.fd`'s `xfdlist` as constant-basis `fd` objects with an all-constant `betalist`: produces a degenerate zero `Fobs` for a functional response (see Decisions above). Use a real functional basis for `betalist` instead.
## Blocked
- **(Eng 1) 4 core parity cases cannot be matched, upstream limit, not a Fabel defect.** `inprod_fourier_L0_0/L1_1/L2_2` and `inprod_basis_bspline_x_fourier` disagree with the exact integral by ~1.3e-4 relative, above core.json's 1e-6 rtol. R's `inprod()` stops its Romberg iteration around 1e-4 and its public API has no tolerance argument; `inprod.bspline` (which fixed the four spline-pair cases) does not accept a Fourier basis. Fabel is the accurate side -- its Gram matrices match R's own `eval.penalty` to 1e-8 in `basis.json`. Kept as strict xfails with the measured reason. Nothing further to try without R private internals, which the clean-room rule forbids.
- **(Eng 1) 3 core + 17 basis parity cases are R defects, closed, not blocked.** `times.fd` (12.8% off the exact product), `^.fd` (5.7e-5), `deriv.fd` for splines (1.3%), plus the 17 basis cases listed in `tests/parity/test_basis.py::R_FDA_DEFECTS`. Each is a place where R returns a demonstrably wrong or coarse value and Fabel is exact; recorded, not to be "fixed".
